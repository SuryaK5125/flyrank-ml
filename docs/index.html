Prioritising Content Review with Machine Learning

A leakage-aware, client-grouped ranking study on anonymised search data.

Surya Kalimuthu

Abstract

Content teams with limited review capacity need a defensible way to decide which pages to investigate first. I framed this as a ranking problem and used anonymised FlyRank search, content and engagement signals with a rule-derived recent-decline proxy as the evaluation target. Logistic Regression and Random Forest models were compared with an impressions-only baseline using a client-grouped holdout that kept all pages from each client entirely in training or test data. On nine unseen test clients, the Random Forest measured Precision@50 of 0.720, compared with 0.520 for the impressions-only baseline, with ROC-AUC of 0.612. These results provide directional evidence for a human-reviewed content prioritisation queue, not evidence of prospective decline prediction or causal benefit from refreshing content.

1. Introduction / Problem

A content reviewer cannot inspect every page every week. The practical decision is therefore not simply whether a page is declining, but which pages should be investigated first when review capacity is limited.

A false positive consumes scarce reviewer time. A false negative can leave a page showing the decline proxy outside the current queue. This makes the problem naturally suited to ranking and motivates Precision@50 as the primary operational metric.

Research question: Can a learned combination of page-level search, content and engagement signals rank content-review opportunities more effectively than a simple demand-based baseline while generalising across unseen clients?

2. Data

The project used two related FlyRank data layers. The production-scale FlyRank internship warehouse, release v20260703, contains approximately 78.8 million daily content-performance rows. I queried its month-partitioned Parquet files directly with DuckDB. The verified March 2026 partition contained 9,841,378 rows spanning 2026-03-01 00:00:00 to 2026-03-31 00:00:00.

The final ranking models were trained on the smaller anonymised starter snapshot containing 30,000 rows and 44 columns. Requiring all final model fields to be present left 19,897 complete-case rows. The warehouse scale therefore describes the broader data environment and schema work; the final model was not trained on 78.8 million rows.

No client names, URLs or raw search queries appear in the public analysis.

3. Methodology

The task is ranking/scoring. The target is the rule-derived proxy trend_direction == "down". The target and its source field are excluded from model inputs.

Fourteen page-level search, content and engagement features were used. The baseline ranks pages only by 90-day impressions. Logistic Regression and Random Forest were then evaluated against the same held-out population.

Validation uses a 70/30 client-grouped split: 20 clients for training and 9 previously unseen clients for testing, with zero client overlap.

A deliberate leakage test added the target-source signal back into the model. ROC-AUC rose to 1.000, confirming why near-perfect metrics require leakage investigation before being treated as model quality.

Random-row validation was substantially more optimistic; the paper therefore reports the client-grouped estimate for unseen-client generalisation.

5. Limitations & Honest Framing

The target is a contemporaneous rule-derived proxy, not a strictly future outcome. Several trailing-90-day features overlap the period used to construct that proxy, so this experiment should not be described as a prospective forecast of future decline.

Complete-case filtering removed 10,103 rows, and the model was evaluated on only 9 held-out clients. Results therefore apply to the evaluated population and should not be assumed to generalise universally.

The analysis is observational. It does not establish that refreshing, rewriting or otherwise editing a recommended page will cause traffic or ranking to improve.

A stronger future design would measure all features before the outcome window begins—for example, features from days 1–90 followed by decline measured during days 91–120.

6. Ranked Recommendations

The model score determines which pages should be reviewed first; it does not determine the final editorial action. Reason codes provide context for a human reviewer.

Archetype Suggested human review
Visible, low CTR Review title, snippet and search-intent fit
Low engagement, visible Review alignment, usefulness and content depth
Thin, visible Review whether important topic coverage is missing
Stale, visible context Check changed facts, SERP conditions and competitors
Model priority only Diagnose manually before deciding whether to edit

Reason codes explain what a reviewer should inspect; they are not automatic edit instructions.

Do not automate: publishing, rewriting, deleting, redirecting, consolidating or refreshing a page solely because the model ranked it highly.
